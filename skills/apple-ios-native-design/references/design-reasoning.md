# 设计推理与交付契约

适用：新功能、多页面流程、较大视觉改版，或需要解释设计取舍。这里的工作方法和模板是 **Skill** 的综合方法，不是 Apple 规定的强制流程。简单修改只使用有关部分。

## 从意图到可检验决策

| 阶段 | 需要明确的问题 | 可核查的输出 | 常见误判 |
|---|---|---|---|
| 任务 | 谁在什么情境完成什么？何时算完成？ | 一句任务目标；主任务与必要辅助任务 | 先画视觉风格，再寻找功能理由 |
| 内容 | 用户首先需要知道什么？数据的单位、时效、归属是什么？ | 内容优先级及数据形态 | 按后端字段顺序铺满屏幕 |
| 信息结构 | 哪些是并列目的地，哪些是对象的下一级，哪些是临时动作？ | 页面关系、导航与呈现方式 | 所有入口都做按钮或所有流程都弹 Sheet |
| 行为 | 进入/完成/取消/返回后会发生什么？哪些状态需要保留？ | 状态与转移契约 | 只有正常完成路径 |
| 空间 | 窗口、大字、键盘、语言、输入方式怎样改变布局？ | 主要自适应规则 | 给每个设备名各画一套固定画布 |
| 表达 | 什么应保持系统熟悉感？品牌在哪些内容中表达？ | 排版/颜色/材质/图标策略与少量理由 | 用更多装饰代替信息层级 |
| 实现 | 现有组件能否满足？目标 SDK/OS 支持什么？ | 原生映射与必要定制的边界 | 为追求新视觉提高最低 OS 或整体重写 |
| 验证 | 哪些观察能证明任务可完成、信息可理解？ | 场景、预期、证据类型 | 把编译成功或单张截图当成体验完成 |

向用户呈现决策结论及简短理由即可；不要求冗长逐步思维记录。

## 用 Apple 原则做取舍

Apple 当前设计原则包含 Purpose、Agency、Responsibility、Familiarity、Flexibility、Simplicity、Craft、Delight。以下是本 skill 对它们的决策化应用；原则存在权衡，不使用固定加权分数声称客观最优。[设计原则](https://developer.apple.com/design/human-interface-guidelines/design-principles)

- 先确认功能是否服务核心任务，再决定其显著程度。
- 让人能理解状态、掌控进度并从错误恢复；将权限和不可撤销行为放在有上下文的位置。
- 优先利用已有交互知识；定制的收益应大于重新学习的成本。
- 把不同文字大小、语言、输入方式与窗口当成设计输入。
- 减少不必要的理解和操作成本；把所有功能藏起来不等于简单。
- 关注细节与情感是否服务该产品：阅读的平静、编辑的掌控、运动的激励可以有不同表达。

## 基础输入：先读项目，再提问

记录已有证据，不要求用户填写表单：

```text
任务与范围：
已有页面 / 导航 / 组件 / 数据契约：
最低部署 OS / 构建 SDK / 目标运行 OS：
支持的窗口与输入方式：
主要内容、主操作与完成条件：
品牌与参考图 / 要保留的行为：
影响决策的未知项与当前假设：
可用验证环境：
```

若是新项目且没有版本约束，在方案中明确建议的支持范围与成本，不能把“按 iOS 27 设计”直接解释为“仅支持 iOS 27”。若用户明确要求完整原生实现，不交付 HTML 仿制品作为等价结果。

## 组件选择的推理粒度

使用 [组件决策树](component-decisions.md) 选出合理默认。只在有真实取舍时比较替代方案，例如：

| 决策 | 选择依据 | 需要比较的成本 |
|---|---|---|
| 详情 Push 或 Sheet | 是信息层级深入，还是可结束的上下文任务 | 返回路径、完成/取消、深链接及状态恢复 |
| List 或自定义内容布局 | 主要是同类对象与标准操作，还是媒体/异构内容 | 阅读密度、懒加载、交互与辅助功能维护 |
| 搜索目的地或局部搜索 | 搜索对象范围与当前信息架构 | 可发现性、结果表达空间、切换后的上下文 |
| 系统或自定义控件 | 标准控件能否表达任务语义 | 键盘、焦点、标签、尺寸、错误处理等行为成本 |
| 图表或文字/列表 | 用户是否需要看关系，而非一个精确值 | 解释成本、数据真实性和无障碍替代 |

不要为已明确的常规选择强制生成三个方案；也不要把视觉偏好写成不存在的 HIG 禁令。

## 状态与转移：按功能选择

每个重要流程至少明确进入、主要操作、离开和错误恢复。以下是检查候选项，不是要求每个页面实现全部状态：

| 状态/事件 | 需要定义的结果 |
|---|---|
| 首次加载 / 再次刷新 | 是否已有可读内容；是否可以继续操作；如何防止布局跳变 |
| 空数据 / 无搜索结果 | 原因不同，给对应说明与下一步；不要共享含糊“暂无数据” |
| 请求失败 / 离线 / 过期内容 | 哪部分可用；保留哪些输入；重试或更新路径；时效是否可见 |
| 编辑中 / 保存中 / 保存失败 | 草稿归属、重复提交处理、是否可离开、失败后继续编辑 |
| 取消 / 交互式关闭 / 系统返回 | 行为一致；根据内容丢失风险决定是否确认或保存草稿 |
| 删除 / 撤销 | 后果范围、恢复能力、不可恢复时的解释 |
| 权限拒绝 / 受限 | 用户还能做什么；重试和设置入口是否适合当前上下文 |
| 前后台切换 / 深链接 / 窗口变化 | 当前选择、导航、筛选与未完成任务是否合理保留 |

只描述应用真实提供的离线、草稿、撤销等能力。缺失能力可以提出建议，不能通过 UI 文案虚构成功或恢复保证。

## 品牌与原生熟悉感

在设计说明中划分系统交互区与产品表达区，按语义而非几何位置判断。导航/操作的常见含义应稳定；内容图片、编辑风格、重点数据、插画与文案可以有鲜明表达。定制组件时写出要保留的状态、手势、尺寸和辅助功能契约。[品牌设计课程](https://developer.apple.com/videos/play/wwdc2026/251/)

## 可直接使用的简短交付模板

```text
设计结果：页面/流程及其服务的任务。
关键选择：导航、组件、内容层级与理由；重大例外及依据。
交互契约：主要操作、返回/关闭、输入保护与相关异常状态。
适配：窗口、大字、语言、外观、辅助功能；新旧 OS 差异。
实现：沿用组件、SwiftUI/UIKit 映射、需要核验的 API。
验证：已执行场景和证据；已知问题、未执行验证及原因。
```

Review 请求改用 [UI Review Checklist](ui-review-checklist.md) 的问题格式。最终反馈随任务规模缩减，不为一处间距改动输出整套设计报告。
